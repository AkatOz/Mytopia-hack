## The script, beat by beat

Four robots work in this demo: Cleaner and Scout, built from the Factory form in beats 1 and 2, each started by the form itself; Courier, built before the group arrives (pre-flight 12) and started from its sheet in beat 4; and Ops Bot, a seed agent, on patrol in beat 5. Research Bot waits at the dock hatch for beat 4's alternative. Every job except the patrol runs its steps once and ends: banner JOB DONE, the robot walks home and sinks into the dock hatch, and START can be pressed again. A robot down in the hatch cannot be clicked, so its sheet and its job picker are out of reach until it runs again; START in the operator panel then runs the job last picked on its sheet, else the job it was built with, else the one that fits its badge. That is why beat 2 picks Scout's next job while Scout is still out. The operator panel acts on the agent whose tab is selected on the card ("acts on: ..."); BUILD and START select the agent they start; a robot's sheet acts on its own robot. The card's tabs wrap onto a second row when they do not fit. START is offered only when the badge is ACTIVE and no run is going. Beside it, the operator panel says what it will run ("run its job: Research the Q3 plan · scripted") or why not ("working now · KILL stops it", "badge KILLED: RESTORE first"). While an inspection panel is open it stands in the card's place and the tabs are hidden: press Esc first and the card returns.

## The honest limits (say them before anyone asks)

- START is a local runner on the demo laptop: the gateway starts `launcher/run.py` as a child process here. In production it would be a runner service (ECS, Lambda or Bedrock AgentCore Runtime), with the agent's secret in Secrets Manager.
- The admin token behind the buttons, the chips, the NEW AGENT form and START is a demo shortcut: one shared header, which the gateway's `/config.js` hands to same-site localhost pages (it refuses a cross-site script tag). So any page served from localhost could START our launcher with one of our jobs. It could never start another program: the runner starts only `launcher/run.py`, from an argument list with no shell, and the job must be a key of `contract/jobs.json`.
- The client secret the Factory mints is written to the launcher's env file on this laptop (`agent\.env`), standing in for a secrets manager. It never appears in a response, an event or a log line. The launcher reads it, the admin token and the Bedrock key from that file; the runner gives the launcher an environment with only the OS basics (PATH, SYSTEMROOT, TEMP and the like) and two Python output settings: no AWS keys, no admin token.
- The AI brain does the whole job in one model turn; the model is offered all six tools, and the gateway decides each call either way. Whether it obeys a planted line is up to the model (at 12:12 AM it did, and again in run 11). Its last words reach the ledger only as the end of the `run_stopped` reason, cut to 160 characters with token-like runs masked; the answer, up to 300 characters, is the `AGENT:` line of the launcher's log.
- The egress rule covers `send_email` only and reads its recipients (`to`), not the subject or the body: it keeps mail inside the company's domains (`EMAIL_DOMAINS` in `gateway\.env`, default `example.corp`); it does not judge what a mail says.
- A call already past the check completes. Revoke, quarantine and kill bite on the next call.
- The gateway, the runner, the launchers and the agents run on this laptop as the same OS user; identity (Cognito), the badges and the log (DynamoDB) and the tools (Lambda) run on AWS. In production the agent gets its own sandbox.
- The six tools are fakes for a fictional Example Corp: `delete_file` answers `deleted <path>` and deletes nothing; `send_email` answers `sent to <to>` and sends nothing. The gateway's decisions are the real part.
- RESET retires every Factory-made agent and deletes its Cognito client, including agents the team made by hand (adam). RETIRE's Cognito delete is best effort: if it fails, the badge row still goes and the `retired` reason says so.
- The quarantine counter, the pulled tools and the runs live in the gateway's memory and start empty after a restart. The chain the inquest reads is in memory too, but a restart reads it back from the local JSONL file (DynamoDB keeps a second copy). Stopping the gateway with Ctrl+C stops the launchers it started and logs their runs as stopped.
- The ledger is tamper-evident, not tamper-proof. TAMPER TEST changes a copy in the browser; nobody has tampered with the real log.
- The Factory's IAM permissions were applied once by hand (`infra/role_policy.py`, Bob, Saturday 7:53 PM). Without them BUILD fails closed with 503 and nothing is half-made.
- The island decides nothing. It draws the rows of `GET /events` and the badges of `GET /agents`; every button only POSTs. A few things come from an HTTP answer instead of a row: the build on the Factory floor (after BUILD's 201), the ticker line after START (its 202) and the sentence of a refusal (a grant above the ceiling, a refused BUILD or START). None of them writes a row.
