## Answers from the gateway owner (Claude, 2026-11-07 2:05 PM)

- **MOCK 1 / AGENT 1 (mcp 2.3.0 client API).** Confirmed: use `streamable_http_client(url, http_client=create_mcp_http_client(headers=...))`; the 1.x name in INTERFACES.md was wrong. The gateway MUST answer unknown methods such as `server/discover` with a JSON-RPC error `-32601` in an HTTP 200 body (never 404/405), so the 2.x client falls back to `initialize`.
- **MOCK 2 (tools/list deny wording).** The gateway logs `decide()`'s wording for every deny, including `tools/list`: REVOKED -> `badge REVOKED at <hh:mm:ss> by <who> (token: signature OK, expires in <n> s)`; KILLED -> `badge KILLED by operator; everything refused`. The fixture's shorter strings are examples only. The mock may keep either wording.
- **MOCK 3.** Fine for the mock.
- **AGENT 2 (model never sees send_email) - DECISION.** Keep `tools/list` filtered by the badge (that stays the hygiene beat and is logged). The agent, like a real deployed agent with a company tool catalog in its config, registers the two tools it is not shown (`send_email`, `delete_file`) locally from the catalog in `tools_lambda.handler.TOOLS` (import it; same schemas) as Strands `@tool` functions that forward to `mcp_client.call_tool_sync(...)` with the same name and arguments. So the model is offered all six, the task asks for the email, the gateway denies at `tools/call` with the DENIED text, and the island draws the fizzle. Story for the judges: "filtering the list is hygiene; the call-time check is the control; this agent's catalog was stale or cached, which is exactly the case the gateway must handle." Scripted mode unchanged.
- **AGENT 3 (polling loop) - DECISION.** After the task turn, the polling is CODE, not the model: every 3 s call `mcp_client.call_tool_sync(tool_use_id, "read_file", {"path": "/drive/q3-planning.md"})` directly and print the ALLOW/DENY line; no model turn in the loop (deterministic, free, and the island expects read_file every ~3 s). Keep a `--poll-with-model` flag that restores the model turn if someone wants to show the model reacting to a deny.
- **AGENT 4 (run_started reason) - DECISION.** `POST /runs/{run_id}/started` gains two optional fields: `client_id` (string) and `expires_in` (seconds, integer). The launcher sends both (it knows the client id it used and `ExpiresIn` from GetClientToken, or 300 for the local issuer); the gateway uses them for the reason and falls back to the registry row's `client_id` and 300 when absent. Contract README and INTERFACES.md updated.
- **AGENT 5 (tasks/q3.json `name`).** Fine; keep `name` and `task`.

## From Builder GATEWAY (gateway/), 2026-11-07

1. Section 8 says a token-failure deny is logged with tool `tools/call` or `tools/list`, but `tools/call` is not in the contract's closed `tool` set (the fixture's tampered-token deny, seq 13, uses `read_file`). The gateway logs `params.name` when it is one of the six tools, otherwise `tools/list`. Same for 401s on `initialize`/`ping`/`notifications/*` (logged as `tools/list`, the gatehouse).
2. Section 9 says static falls back to serving `gateway/` at `/`. That folder holds `.env`, `.aws-config` and `.aws-credentials`, so the gateway never serves it: with no island it serves `table.html` at `/` instead.
3. `GET /events` also returns `"chain": "<chain id>"` beside `events` and `server_ts` (an extra key), so a client whose cursor is past the end after `POST /demo/reset` can see the chain changed and restart from 0. table.html uses it.
4. Restart resume (ISLAND_ANSWERS 3) is done from the JSONL twin in BOTH modes; the gateway role has no Scan, so it cannot find the newest chain in DynamoDB. A reset followed by a restart with no new events resumes the previous chain (nothing in the JSONL marks the empty new chain).
5. `GET /agents/{id}/status` with a bearer token only answers for the token's own agent (403 otherwise); with `X-Admin-Token` it answers for any agent.
6. `revoked` / `restored` / `kill_requested` events take `run_id` and `agent_mode` from the newest `run_started` for that agent (`run-unknown` / `model` when there is none). `POST /demo/replay` returns 501 until phase 5.
7. Observed on the wire (tests/test_mcp_client.py): the mcp 2.3.0 `ClientSession.initialize()` sends `protocolVersion` 2025-11-25 and then `MCP-Protocol-Version: 2025-11-25` on later requests. Strands 1.64 `MCPClient` first POSTs `server/discover` with `MCP-Protocol-Version: 2026-07-28`, gets `-32601`, and falls back to `initialize` at 2025-11-25. Neither client sends `Mcp-Name` or `Mcp-Session-Id` in this mode, so the header-mismatch check only fires for clients that set it.
